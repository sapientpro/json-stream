# 2.0.1 release benchmark

Measured on 2026-10-05 on an Apple M4 Pro: Node 26.10.0 and Bun 1.4.2.

Baseline: published **2.0.0**, commit `a0a71619efea94163a6f61df0564d12126961b76`. Candidate parser: merged main `a5d23c26c00adbe64f413c0f095a23434ea47397`, packaged as **2.0.1**. Neither v3 API prototypes nor a JSON.parse parsing shortcut are included.

Parser and Subject sources for both versions are compiled identically as ESNext ESM with native private fields. The baseline generated modules are byte-identical to the published npm ESM modules after adjusting only the local import extension. Prepared UTF-8 buffers are sliced into equal chunks before timing. Both versions perform the same output work through the existing public API: root materialization, wildcard item/ID callbacks, decoded string fragments, or discard with `retainRoot: false`. JSON.parse is used only to prepare expected fixture values outside timing.

Each version/case runs in three independent processes, with alternating version order. Each process performs 200 warmup parses and seven samples of 16 parses; tiny documents use 2000 warmups and 2000 parses per sample. GC runs before each sample. Figures below use the median of the three process medians, in decimal MB/s. Correctness assertions run outside timed samples; fragment reconstruction is checked once before timing. This is a throughput measurement, not a peak-memory measurement or a general cross-machine guarantee.

## Interpretation and limits

The matrix includes every measured case, including negative changes. Small changes can reflect process/JIT/GC variance; raw process medians and all samples are included below. Gains in numbers, literals, escaped strings and observer dispatch do not imply the same gain for UTF-8 decoding or every materialized object. Discard, items and root outputs perform different work, so compare versions within a row rather than treating rows as interchangeable parser modes.

The Bun adaptive Unicode cache targets repeated code units. An earlier comparison against the immediate pre-cache parent found a regression on a rare all-distinct 65,536-code-unit escape workload (about −7.3% ESM, −2.3% CJS). That is a different baseline and is not represented by this repeated-escape fixture. The cache is bounded and adaptive; this release does not claim universal gains on escape-heavy data.

These timings measure ESM on Node 26 and Bun, not CJS throughput or Node 22/24/Deno throughput. The supported packaging/runtime checks below cover those separately.

## Release validation

- Full Jest suite passed on Node 22.23.3, 24.21.0, 26.10.0 and Bun 1.4.2.
- TypeScript CJS/ESM builds passed; the public exports, Node engine requirement and all eight declaration files are identical to published 2.0.0.
- The actual packed tarball passed ESM consumer smoke checks on all four runtimes plus Deno 2.9.7, and CJS checks on Node 22/24/26 and Bun. Consumers ran outside this repository to avoid self-reference imports.
- `@arethetypeswrong/cli --pack .` found no export/type-resolution problems.
- The tarball excludes research notes, benchmark scripts and tests.
